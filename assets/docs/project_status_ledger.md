## Purpose and authority

This is a status index for stable capabilities and project components, not a development diary, issue tracker, or release approval. The 2026-09-25 checkpoint validated the supported local timeline boundary from a clean `develop` tree: exact Ollama `qwen3.5:2b` safely failed closed to a source-backed, date-precise fallback with preserved local/Ollama/model provenance, while exact `qwen3.5:9b` produced three grounded source-backed events that rendered and survived reload. The 2B structured-output result is a model/task compatibility limitation, not an unfinished application gate; it is no longer an actionable retry target unless the model, prompt, or timeline implementation changes. Historical `unknown` runs remain unattributed evidence, and broader provider, hosted-CI, credential, source-refresh, release, and container gates retain their independent statuses.

The component scope, status, and next action below are current truth. The evidence links point to the detailed architecture, validation, QA, or runtime documents that explain how a claim was established. The dated [`runtime/validation_ledger.md`](runtime/validation_ledger.md) remains the detailed validation register and diary; it is evidence for this ledger, not a competing current-status authority.

## Maintenance rules

Future coding and validation sessions must:

1. Inspect this ledger before substantial implementation or validation work.
2. Use it to identify known defects and previously validated behavior.
3. Update affected component rows after implementation changes.
4. Update evidence and validation dates after meaningful tests or manual checks.
5. Never mark a component `VALIDATED` without supporting evidence.
6. Downgrade a status when a regression or new limitation is discovered.
7. Close or move an issue to the resolved section only after remediation and revalidation.
8. Avoid duplicate issue entries for the same underlying defect.
9. Link detailed reports instead of copying their narratives into this file.
10. Keep this ledger synchronized with the checked-out repository and its current evidence boundary.

`Last Validated` means the latest meaningful evidence for that component, not the date this document was edited. A status is always limited to the scope stated in the same row. A `VALIDATED` row does not imply that every adjacent workflow or the release is ready.

## Status taxonomy

| Status | Meaning |
|---|---|
| `VALIDATED` | Implemented and confirmed through meaningful testing for the stated scope. |
| `WORKING` | Believed to work from implementation and limited testing, but not fully validated for the stated scope. |
| `PARTIAL` | Implemented, but incomplete, degraded, variable, or valid for only part of the expected behavior. |
| `BROKEN` | Known not to work correctly for the stated scope. |
| `BLOCKED` | Cannot currently be validated or completed because of an external dependency, missing credential, unavailable service, hardware constraint, upstream issue, or equivalent blocker. |
| `UNVALIDATED` | Implementation exists, but available evidence is insufficient to claim that it works. |
| `NOT_IMPLEMENTED` | The expected capability is absent from the current repository. |
| `DEPRECATED` | Intentionally retained for compatibility or scheduled for removal. |

The older validation reports use run-specific terms such as `PASS`, `ATTENTION`, `FAIL`, and `NOT TESTED`. Those terms remain meaningful inside their reports; this file translates them into the taxonomy above. No current component is marked `BROKEN` solely because an older report contained a resolved finding.

## Evidence boundaries

- A test result is evidence only for the component scope and environment stated in its source report.
- Historical reports remain useful for provenance, but later remediation or newer evidence controls the current row.
- Provider/catalog reachability is not clinical correctness, and a browser-rendered surface is not proof of an end-to-end workflow unless the report says the workflow completed.
- Synthetic data, local source mode, dev bundles, and focused test slices are labeled as such. They do not become clean-machine, hosted, packaged, or release evidence by implication.
